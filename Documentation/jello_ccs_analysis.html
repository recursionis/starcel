Abstract

We instrumented the combinator-tree builder in jello/src/draw.py (Jello, a Python wrapper for the Jelly tacit-programming language) to expose the full set of combinators emitted while reducing a representative 1-1-2-q-s-2-2-2-s-q-1-1 chain (twelve surface tokens). Eight combinators are emitted (B × 5 — 4 visible plus 1 invisible — h₁ × 2, Φ₁ × 1), but only the four visible Bs reach the linearized "combinator-chain sequence" (CCS) BBBB printed by Grid.ccs(). The remaining four are dropped either by name (the h₁s) or by position (non-leftmost labels on a row). We then ran seven probe variants to falsify a naïve "trailing tokens add trailing Bs" hypothesis embedded in the project's README. The probes confirm an alternative rule: each leading monad contributes exactly one B; the remaining structure of the chain is a separator-bounded composition of pre-canned sub-chains. We close with fourteen open research questions touching algebraic structure, type theory, comparability with BQN trains, and possible integration with the Hans Boehm constructive-reals library already vendored alongside this project (see also the sibling constructive_reals.html).

1. Project Context

Jello is a Python script (jello.py) that wraps the Jellyfish executable — a fork of Dennis Mitchell's Jelly tacit-programming language. The wrapper exposes long-form English-like names (e.g. iota, prior, scan) for Jelly's single-byte atoms (R, ṕ, \) and prints, for each user expression, both the value and a combinator-tree showing how the chain decomposes into Currying combinators (B, S, Φ, Σ, Δ, …) plus Jello-specific lifts (h₁ for unary quicks like prior and scan).

The package lives at Content/Scripts/nd_table/jello/ inside a larger Unreal Engine 4.27 project (Starcel9). Jello is listed in the project's engineering roadmap (ENGINEERS.md, line 16) as a planned IDE feature: "Monadic, diadic, triadic, and n-adic chains https://github.com/codereport/jello (extend to Applicatives and Functors) with Code Smells". Adjacent directories include reals-0.0.6/ — a Python port of Hans Boehm's SGI/HP constructive reals library (the UnaryCRFunction.java source shared during this investigation belongs to that family; see constructive_reals.html). Other neighbours include foam, pga_renderer.py, and ndtable.py, but they did not figure into this brief.

3. The Triggering Image

The investigation began with a screenshot of the Jello REPL evaluating this expression. The screenshot (terminal-window styled, dark background, traffic-light header reading "Jello") contained four logical zones:

  1. Prompt line: > [2,4,3] :: iota flat < prior : + * r . scan maxr add1 with surface tokens colored (monad green, dyad blue, quick red).
  2. Atom row: R F < ṕ ð + × ṛ µ \ Ṥ ‘ — one atom per surface token, horizontally aligned beneath the prompt.
  3. Trace block: ten rows showing each prefix of the atom string and what jelly eun returned for it on [2,4,3]. See §4.
  4. Combinator footer: the chain-arity string 1-1-2-q-s-2-2-2-s-q-1-1 followed by "monadic chain (BBBB)" and an ASCII tree growing downward, with brackets ┌——┐ at top and combinator labels (B, h₁, φ₁) below.

Visual note worth flagging: the image draws brackets as ┌——┐ opening downward; the code in grid.py writes └——┘ opening upward (constants START="└", END="┘", MID="┬"). The image likely has the tree visually inverted relative to the code's grid for human readability. We did not reconcile this — see Q13.

5. Chain-Arity Decomposition

The chain 1-1-2-q-s-2-2-2-s-q-1-1 is recursively split by separators (s) into three sub-chains, each typed by its preceding separator:

Sub-chainArityTokensChain typeTriggered by
11-1-2-qiota flat < priorouter (monadic) or outer (dyadic)start of chain
22-2-2+ * rdyadic: (dyadic separator)
3q-1-1scan maxr add1monadic. (monadic separator)

After each sub-chain reduces to a single element on the stack, the outer pass concatenates them and re-runs the quick/monad/dyad reduction at the outer level. The scan quick is a prefix in sub-chain 3; because combinator_tree returns prefix quicks unchanged, scan bubbles up to the outer level, where it picks up sub-chain 2's result via an h₁.

7. The Visible-B Mapping

Grid.ccs() linearizes the grid by taking the leftmost-stripped first three characters of each row, dropping rows whose first char is a vertical bar (⋮), then stripping the residual box-drawing chars and repeatedly removing the substring "h₁". The grid has eight rows (rows 0..7 = lvl×2 brackets + lvl×2+1 labels for four levels). After the filter, only label rows 1, 3, 5, 7 contribute, and only the leftmost label on each row survives the [0:3] slice.

10. The CCS Counting Rule (Hypothesis)

For chains of the form 1{k} … s … s … 1{m} (k leading monads, m trailing monads, with separator-bounded internals):

Empirical rule (piecewise): |CCS|B = k + 2 if the .-tail has ≥1 monad, otherwise |CCS|B = k + 1. Here k is the count of leading monads, and the chain has two separators dividing it into three sub-chains.

Probe-to-rule mapping: P1: k=0, m=2 → BB; P2: k=2, m=2 → BBBB; P3: k=1, m=2 → BBB; P6: k=2, m=0 → BBB; P7: k=3, m=2 → BBBBB.

  • The +2 is the outer collapse: three sub-chain results need two Bs to fold into one. This is a constant for this chain topology.
  • The +k is the leading sub-chain's internal collapse: starting from 1k2q, the quick consumes the dyad, leaving 1k+1, which then needs k Bs to fold to one. (k=0 → 0 inner Bs, leaving only the +2 outer = BB, matching P1.)
  • The trailing sub-chain's Bs are not leftmost on row 1 once a leading sub-chain exists — they remain invisible regardless of m. The .-subchain only needs at least one monad to contribute the structural element that the outer top-B consumes; reducing to zero monads (P6) collapses to BBB (the outer "+2" loses its third arm).

This rule was confirmed against probes P1–P7. It has not been proven in general; see Q1.

11. The Wrong Bullet & Its Fix

Original (wrong) bullet in README.md Example 4 (authored under D2, with the maxr add1 claim that later proved wrong):
"The chain collapses to BBBB: the leading iota and flat contribute two Bs, prior and scan each lift their preceding chain through h₁, the + × ṛ body between the : and . separators forms a Φ₁, and the trailing maxr add1 adds the final two Bs."

The claim in bold is empirically false. Probe P4 (drop maxr) and P5 (swap maxr→add1) both yield BBBB, proving the "final two Bs" do not depend on the pair maxr add1.

Fix applied (README.md line 119) — applied via workflow wcqrrrd9t, see D8:
"The chain collapses to BBBB: a row-1 B fuses iota and flat, a row-3 B lifts that through an h₁ over <+prior (quick), a row-5 B joins the left tree to a Φ₁ over + * r lifted by another h₁ through scan (quick) across :, and a row-7 B joins everything to the .-subchain scan maxr add1 (the scan quick having bubbled up via h₁ at M5 into M6 already, so M7's right arm is just maxr add1 via M4's B)."

Residual overfit, noted but not corrected: the fix still says ". subchain maxr add1" — a generalization (just "any monadic terminator") would also fit probes P4 and P5. We left it specific because surrounding Examples 1–3 are equally chain-specific.

14. Open Research Questions (for the recipient)

The recipient is the intended source of "bleeding-edge research" feedback. These questions are ordered roughly by ratio of payoff to plausible accessibility — early ones are tighter and more concretely answerable, later ones are speculative.

Q1

Prove or refute the CCS counting rule

The rule |CCS|B = k + 2 (for k leading monads, with two separators dividing into three non-empty sub-chains, and at least one monad in the .-tail) was confirmed against probes P1–P7. Is it provable from combinator_tree's recursive structure? Are there chain shapes where it breaks? What is the closed form for |CCS|B as a function of (k, m, separator-count, internal arity vector)?

Q2

Is ccs() a faithful linearization?

The current Grid.ccs() emits only the leftmost first-3-chars of each label row. It loses Φ₁, h₁ (intentionally stripped by name), and non-leftmost Bs. Is there a canonical complete linearization (analogous to in-order tree traversal) that uniquely identifies the chain modulo provable equivalences? If so, would the README's tutorial sections (Section 4.x) better use it?

Q3

Generalize the ".-subchain" descriptor

The fix bullet says "the . subchain maxr add1", but P4–P5 show B#4 only requires some monad in the .-subchain (zero monads, P6, drops the count). What is the right phrasing for an Example bullet that is both chain-faithful (matches the surface text the reader sees) and rule-faithful? Is there a community convention?

Q4

Empty-leading-sub-chain regression (reframed from a test.py:62 TODO)

The TODO at test.py:62 (# noqa unit_test("+ * r . scan maxr") # 2.2 TODO) tests a chain with no leading-monad sub-chain at all — only a dyadic mid-chain and a monadic .-tail, no opening :. Reframed as a research question: do chains with an empty leading sub-chain (no leading monads and no leading dyad-quick pair) form a regression case where the k + 2/k + 1 piecewise rule from §10 still applies, or does the absence of the first separator collapse the +2 outer-fold constant to +1? Either resolve in-tree (run draw.combinator_chain_sequence on the chain, add the assertion) or investigate whether combinator_from_pattern_match has a missing case.

Q5

Fill the gaps in the dyadic chain table (README §"Dyadic Chains")

Row 1 (+ × 1 …, type 2-2-0, "dyad-dyad-nilad") has empty IC and SC cells. The combinator table beneath ("Combinator Table (WIP)") is explicitly WIP, listing only S, B₁, E, ε. What are the missing combinators? Is there a principled way to derive them from Φ.₂, Δ, etc.?

Q6

CCS-preserving compilation from BQN k-trains to jello chains

Does there exist a CCS-preserving compilation from BQN's k-trains (1-train, 2-train, 3-train, Atop, Over) into jello chains? For every BQN tacit expression e, is there a jello chain c such that |CCSB|(c) equals the syntactic train-depth of e? Identify BQN constructs (likely deep modifiers) with no chain analogue.

Q7

Mine the algorithm-advisor equivalence lattice

The advisor at algorithm.py hard-codes ~30 rewrites (e.g., + scan → sums, deltas > 0 → < prior). Can the full equivalence lattice for chains of length ≤ 10 be enumerated mechanically — e.g., by running every chain on a battery of inputs and clustering by output, then verifying provable equivalence on each cluster?

Q8

Integrate constructive reals

The user shared Hans Boehm's UnaryCRFunction (SGI/HP constructive-reals library, also vendored as reals-0.0.6/ in the project — see the sibling brief constructive_reals.html). What would jello tokens look like when evaluated against CR instead of integer Jelly atoms? Specifically: scan, maxr on infinite-precision floats — are they well-defined in the limit, or do they require explicit precision-management?

Q9

Chain Kolmogorov complexity

For a function f with a finite description (e.g., "longest strictly-increasing run length"), what is the shortest jello chain computing f? Decidable for finite input/output domains, but is there an efficient search? Could the --find-by-example facility (currently brute-force over monadic-pair compositions) be extended to chains of length 3–6?

Q10

Give h₁ a principal type

The h₁ glyph appears 2× in our trace and is stripped from CCS by name. Its role is to "lift a dyadic chain to monadic" when a unary quick (prior, scan) grabs the preceding dyad. Is h₁ = BWB in SKI-BWCK? Is it Smullyan's Warbler (Wxy = xyy)? Is its System F type ∀a b. (a → a → b) → (a → b)?

Q11

Why exactly four rows? Combinator-tree depth as function of token count

Our 12-token expression produced a 4-level tree (label rows 1, 3, 5, 7) and exactly 4 visible Bs (5 emitted; M4 dropped by leftmost-on-row filter). Is the tree depth a monotone function of token count? Are there pathological chains whose tree grows superlinearly?

Q12

The missing Φ-family

The combinator table lists Φ₁ (2y222, all dyadic args), Φ (1y121), Φ.₂ (2y122). There is no Φ₁.₃ or analogous for 2-2-1. Is this an intentional omission (those reduce to nested S/B₁) or a real gap?

Q13

Tree-drawing convention: APL root-down vs concatenative root-up

The triggering image (§3) draws the tree root-down (APL/J/BQN convention) with brackets ┌——┐; grid.py draws root-up with └——┘ (constants START="└", END="┘", MID="┬"). Is this two valid conventions colliding, or a stale screenshot? Resolve: (a) does grid.py.display() apply a vertical flip, or is the image stale; (b) which convention should jello adopt for consistency?

Q14

Recursion bound on separators

This chain has two separators. combinator_tree handles them via recursion. What is the upper bound on separator nesting that the current implementation correctly handles? Are there chains with 3+ separators whose CCS depends on the order of recursion?

16. Reproducibility Appendix

Single-command reproducibility

All of the analyses in this document — the instrumented trace from §6, the canonical P1–P7 probe suite from §9/§10, the §7/§11 chain comparisons — can be reproduced via a single CLI: Content/Scripts/jello_ccs_probe.py. The script imports draw, jello, grid, and utils directly from Content/Scripts/nd_table/jello/src/ (no modification to the jello package) and reconfigures sys.stdout to UTF-8 at top-of-file, so no PYTHONIOENCODING env var is required on Windows.

# Single chain (default)
python Content/Scripts/jello_ccs_probe.py "iota flat < prior : + * r . scan maxr add1"

expr = 'iota flat < prior : + * r . scan maxr add1'
